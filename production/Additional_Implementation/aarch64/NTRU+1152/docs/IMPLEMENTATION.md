# NTRU+1152 for AArch64: implementation notes

The KEM flow is Official's (`kem.c`). Key generation samples f and g, maps them
to the transform domain and inverts them there; encapsulation and decapsulation
use transform-domain products, and decapsulation inverts the transform and
reduces to {-1, 0, 1}. This page records the contracts between the kernels, the
bounds they rely on, what `make check` verifies, and the constant-time and
cleanup policy.

## Representations

Polynomials are `int16_t[1152]` in R_q = Z_q[X]/(X^1152 - X^576 + 1),
q = 3457. Transform-domain coefficients are in the Good-Thomas (GT) order, not
wire order. Montgomery scales are written R^k with R = 2^16: an "R0" value
carries no factor, an "R^-1" value one factor R^-1.

| Kernel | Input | Output |
|---|---|---|
| `poly_ntt` (Forward) | every coefficient in [-3, 4] | transform domain, R0, not reduced |
| `poly_baseinv` | Forward output | the inverse of every leaf, R0; returns 1 and clears the output if a leaf is not invertible |
| `poly_basemul`, `poly_basemul_add` | transform domain, R0 | R0, abs <= 3,024 |
| `poly_basemul_rinv` | canonical coefficients, in [0, q) | R^-1, abs <= 2,458; decapsulation's first product only |
| `poly_invntt_ternary` | the output of `poly_basemul_rinv` | coefficient domain, in {-1, 0, 1} |
| `poly_frombytes` | 1,728 bytes | the decoded coefficients; returns 1 if any is `>= q` |

The Forward kernel's first split multiplies without reduction, so it requires
every input coefficient in [-3, 4]. The KEM's inputs (f, g, r, the encoded
message and the recovered m) all satisfy this; it is not a general polynomial
transform. `poly_basemul_rinv`'s inputs are canonical because decapsulation
aborts unless both of them decode.

## Decapsulation inverse

`poly_invntt_ternary` (`inverse_ntt.S` with `inverse9.S`, `inverse16.S`,
`inverse16_tail.S`, `crepmod3_raw.S` and the tables in `inverse*_tables.h` and
`invntt9_lane_tables.h`) inverts the transform and reduces to {-1, 0, 1}. It
consumes the R^-1 output of the first product directly, and
`poly_basemul_rinv` writes that output in the lane order the inverse reads, so
no pass reorders it in between.

- **Ternary reduction.** The map from a raw coefficient to {-1, 0, 1} uses a
  single correction by q, which is exact for abs <= 5,185 because q = 1
  (mod 3).
- **Range.** An interval analysis of the linked executable's disassembly shows
  that for every input with abs <= 2,458 no intermediate value leaves
  `int16_t` (peak 22,122), the output is in {-1, 0, 1}, and every input to the
  correction has abs <= 5,178, inside the 5,185 above. The analysis holds up to
  abs <= 2,501. The analysis tool is not part of this package.
- **Scratch.** 2,304 bytes, owned by the caller: `kem.c` overlays it on buffers
  that decapsulation clears before it returns.

## Batch inversion

`poly_baseinv` (`inverse.c`, with the numerator and final-scaling steps in
`baseinv_num.S` and `baseinv_finish.S`) inverts the 288 leaves
Z_q[X]/(X^4 - zeta) of the transform domain with one field inversion. Degree 4
is a quadratic tower: with u = X^2 and u^2 = zeta, inverting a leaf is two
nested quadratic conjugations, whose +,-,+,- signs are applied in the final
scaling. The prefix products run as three independent chains of twelve steps.

A leaf is not invertible exactly when its norm is zero. About 29% of the
candidates for f and g have such a leaf, so `poly_baseinv` declassifies the
result and returns early (a branch-free failure path costs key generation 1.1%
on the Cortex-A76); it zeroes its output and returns 1, and key generation
draws a new sample, as Official does.

## Serialization

`pack.c` serializes a transform-domain polynomial, with the tables in
`codec_pairs.h`; the coefficients are in GT order, so the serializer also
applies the fixed GT-to-wire permutation.

- `poly_tobytes` accepts any `int16_t`: a Barrett step lands in (-q, q), then
  `add q` and an unsigned minimum pick the canonical representative (exact for
  all 65,536 inputs). `poly_tobytes_small` requires every coefficient in
  (-q, q) and applies only the last step. The small entry serves h and
  f * g^-1 in key generation, c in encapsulation and the second product in
  decapsulation, all outputs of `poly_basemul` or `poly_basemul_add`; the full
  entry serves f, r (through `hash_g_fr0`) and the re-encryption.
- A twelve-byte block takes one 16-byte store when its four extra bytes land in
  the next block and that block is written later: 66 of the 144 blocks. The
  pair order, lane order and store kinds were generated by a script that also
  simulated every byte write; the script is not part of this package.
- `poly_frombytes` is `unpack.S`, generated from `codec_pairs.h` (the generator
  is not part of this package): one two-register `tbl` per block pair and half
  does the first level of the transpose and the byte expansion together. It
  returns 1 if any coefficient is `>= q`.

## Hashing

SHAKE256 is the public-domain sponge in `fips202.c` over mlkem-native's
Keccak-f[1600] permutations: `keccakf1600.S` (scalar), `keccakf1600_v84a.S`
(FEAT_SHA3, used when the compiler targets it) and `keccakf1600_x2_v84a.S` (two
states at once, FEAT_SHA3). NTRU+768 and NTRU+864 carry the same three files.

- `shake256_prefixed` absorbs a domain byte and a message without building
  their concatenation; `hash_f`, `hash_g` (through `hash_fixed.c`) and `hash_h`
  use it.
- Key generation expands the seeds of f and g with `shake256_x2`, which
  permutes both states at once with FEAT_SHA3 and makes two single-state calls
  otherwise. It draws the next seed before trying f, so `randombytes` sees the
  same calls in the same order as with Official.
- `hash_g_fr0` serializes r with the full entry into a local buffer and hashes
  it with the prefixed sponge, so r's bytes never pass through the ciphertext
  buffer.
- SUPERCOP builds (`-DSUPERCOP`) always use the scalar permutation, the only one
  the exported leaf carries.

## Validation

`make check` runs:

| Target | Checks |
|---|---|
| `manifest-check` | the tree holds only release files (`scripts/check_release.py`) and every file matches `SOURCE-MANIFEST.sha256` |
| `tests` | the clear sites, the declassify sites and the 32 SIMD register wipes in the sources (`scripts/check_zeroization.py`); 64 key pairs, encapsulations and decapsulations, each followed by a tampered ciphertext (`test_kem`); a coefficient q, q + 1 or 4095 at each of the 1,152 positions of pk, ct and both halves of sk is rejected with cleared outputs (`test_canonical`, 13,824 cases); callee-saved registers across the KEM functions, the kernels, the fixed-length hashes and the Keccak permutations (`test_abi`); rejection with a cleared output for a non-invertible leaf at each of the 288 positions, with and without aliasing (`test_baseinv_fail`); at run time, that the clears leave zeros (`test_zeroization`) |
| `kat-check` | the generated KAT equals `kat/expected/`, Official's vectors |
| `export-check` | the SUPERCOP export is deterministic |
| `keccak-v84a` | the FEAT_SHA3 permutation equals the scalar one on 100,003 states (skipped without FEAT_SHA3) |
| `shake-prefixed` | `shake256_prefixed` equals `shake256` over the built concatenation |

The register wipes are checked in the sources because neither test sees them:
the runtime audit observes only the clears made through `secure_clear`, and the
ABI test checks that callee-saved registers are preserved, not that the others
are erased.

## Constant time

- SUPERCOP's TIMECOP (`TIMECOP=256`) passes for the exported leaf at `-O`,
  `-O2`, `-O3` and `-Os`.
- The only values declassified are the two that Official releases by design:
  whether a secret key decodes canonically (decapsulation) and whether a key
  generation sample is invertible (key generation retries).
- Branches and memory addresses depend only on public data; tables are indexed
  by public constants.

## Cleanup policy

- Secret data with a lifetime is cleared in C with `secure_clear` (a plain
  clear and a compiler barrier; `SecureZeroMemory` on Windows): keys, inverses,
  coins, messages, hash buffers and the polynomials derived from them. The
  generic SHAKE API also wipes its state and buffers.
- Kernel working buffers are not wiped. The Forward transform takes its
  scratch from a wrapper in `api_glue.c`, so no kernel allocates memory that C
  cannot reach, but that scratch is not erased, and neither are the batch
  inversion's local arrays in `inverse.c`. Decapsulation's inverse takes its
  scratch from `kem.c`, which overlays it on buffers that are first written
  after the inverse and cleared on exit.
- The inverse erases the SIMD registers (v0-v31) before it returns: register
  state, unlike a stack frame, is not overwritten by the code that runs next.
- There is no promise about stack frames, compiler spill slots, caches, swap or
  microarchitectural state.
